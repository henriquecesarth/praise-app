# M20-C14 R8 - PDF marker clipping

Scope: only the captured PDF header inside #printable-sheet-pdf. Existing WIP retained; no deployment, backend/mobile/Firebase/API or general UI changes.

## Cause and baseline evidence

The 190mm source/header measures 718.109375 CSS pixels. The original right-aligned marker ended at exactly the capture boundary (0px clearance, 0px right padding). Its intrinsic flex sizing and the title's unconstrained intrinsic width also allowed long unbroken strings to overflow the captured source. Baseline actual-PDF tests recorded both conditions: before/reported-metrics.json and before/long-both-metrics.json. The latter has sourceOverflow=true. This leaves no guaranteed glyph/raster safety inset; the fix supplies one rather than widening A4 or hiding text.

The reported title/marker were reproduced with synthetic artist/lyrics, without reading or modifying the real Staging record. Initial local output verified the edge condition; the full specific owner document/font environment was not accessed.

## Minimal fix

- Header width 100%, box-sizing border-box, 2px right padding inside the existing 190mm content area.
- Left group/title and marker receive explicit width/min-width constraints. Marker flex is 0 1 auto and remains right-aligned with margin-left auto.
- overflow-wrap: break-word permits controlled wrapping of long tokens. An interim anywhere rule wrapped correctly in DOM but failed to wrap the text drawn by the actual raster engine; real-PDF visual inspection caught this and break-word was validated instead.
- No ellipsis, clipping, expanded page width or changed export margins. Existing generation, cache, page slicing and download implementation unchanged.
