## R4-M15 remediation and validation

Working branch: `fix/r4-m15-release-blockers` (from `8038bf5b1ec8acf0c6ee9e900ed7f3e64d8d3322`).

### Root causes

1. **Blocker A (Historical link aliases):** `RepertoireRepository.synchronizeLinks` categorized primary-version links strictly via `!link.isCustom && fields.find(...)`. Legacy documents whose primary version stored `YouTube`, `MP3`, or `Chord` links with `isCustom: true` backing `youtube_url`, `audio_url`, or `chord_sheet_url` were reclassified into `external_links` whenever `versions[0].links` was resubmitted (such as during a version rename), clearing the flat compatibility field and breaking `has_youtube` filtering.
2. **Blocker B (Orphan classifications cleared by unrelated edits):** `CreateSongModal` omitted unchanged `bpm` values on existing versions during save, but always resubmitted `classificationIds` (which `mapSongToApi` serialized as both `classificationIds: []` and `classification_ids: []`). When a document had an orphaned flat `classification_id: "deleted"` and `versions[0].classificationIds: []`, the Backend interpreted the resubmitted empty array as an explicit clear and overwrote `classification_id` with `null`.

### Chosen compatibility contracts and important decisions

- **Historical alias preservation (`RepertoireRepository.ts`):** `updateSong` passes `existing` into `synchronizeLinks(base, patch, explicitLinks, existing)`. For each standard flat link field (`chord_sheet_url`, `youtube_url`, `audio_url`), if `existing[field]` is non-empty, `existing.versions[0].links` has no non-custom standard link for that category, and `existing.versions[0].links` contains a custom-flagged (`isCustom: true`) alias link matching that category and URL that is not owned by `existing.external_links`, the corresponding link in `base` is tracked in a `WeakMap<SongLink, LinkField>` as belonging to that legacy flat field. Deliberately custom links created via `external_links` or when the flat field is null remain in `external_links`.
- **Classification omission vs explicit clear (`CreateSongModal.tsx`, `VersionEditModal.tsx`, `types.ts`, `RepertoireRepository.ts`):** Rather than guessing intent from an identical empty array in the Backend, `VersionEditModal` tracks `classificationsTouched` (preserving `version.classificationIds` verbatim when untouched and filtering out nonexistent orphan IDs when the user actively toggles chips) and `CreateSongModal` tracks `touchedClassificationVersionIds` per version ID. On save, `CreateSongModal` omits `classificationIds` from existing version patches when `!touchedClassificationVersionIds.has(version.id)` and `sameClassificationIds(previous.classificationIds, version.classificationIds)` is true. Unchanged edits omit `classificationIds`/`classification_ids`, preserving flat orphans (`classification_id: "deleted"`), while explicit clears (`classificationIds: []` or `classification_id: null`) unambiguously clear the classification to `null`.
